# Cluster Orchestration: Current State and Proposed Design

**Status: the secure cluster, quorum, failover, and common management API below are proposed, not implemented.** Existing discovery and remote-launch paths are experimental building blocks, not high availability or a security boundary.

## Current implementation and limits

- [The DIPC router](../src/ipc/router.zig) routes local messages or hands remote messages to `netd`; [netd](../src/user/netd.zig) contains a virtio NIC driver and an IPv6/DIPC networking path. [clusterd](../src/user/clusterd.zig) and its [protocol](../src/user/protocols/clusterd_protocol.zig) provide discovery, resource advertisements, remote launch requests, and telemetry. A request or timeout does not establish safe ownership transfer or failover.
- [DIPC authentication](../src/ipc/dipc.zig) uses a cluster-wide shared HMAC key. The [Phase 7 record](PHASE_7_ROADMAP.md) explicitly identifies the lack of replay protection. Any holder of that shared key can impersonate another node; it is neither an individual node identity nor encryption. The existing virtio/DIPC bridge does not provide a secure guest vSwitch, policy, guest identity, or encrypted overlay.
- [Boot initialization](../src/main.zig) computes a software kernel hash and can compare it against a configured expected hash; absent that hash it is permissive. [The manifest](../src/kernel/trust.zig) and [service verification](../src/services/service_manager.zig) are not evidence of UEFI Secure Boot enforcement, TPM-backed measured boot, remote attestation, or a hardware-protected node identity. Those capabilities require separate future implementation and validation.
- [windowd](../src/user/windowd.zig), [dashd](../src/user/dashd.zig), and [configd](../src/user/configd.zig) provide pieces of a native interface and telemetry; they are not yet a complete, authenticated cluster UI backed by one authoritative management API. The existing [two-node cluster smoke script](../test_qemu_cluster.sh) checks discovery, remote launch, and telemetry markers, not secure enrollment, quorum, fencing, or failover.
- [storaged](../src/user/storaged.zig) has an NVMe path, fails block requests when no NVMe is available, issues NVMe Flush when Identify Controller reports a volatile write cache, and handles virtio FUA with a write-then-flush fallback. QEMU write/flush/readback does not establish physical power-loss durability, native NVMe FUA, crash recovery, quorum, or durable replication.

## Design boundaries and assumptions — proposed

Future Catenary platform code is independently authored, not copied or adapted from another platform. Published specifications and well-understood protocols may guide the design; use approved, reviewed cryptographic primitives rather than inventing cryptography. Direct Type-1 execution is the primary path for both MicroVMs and full VMs; a support VM or nested virtualization is optional, never a bootstrap or recovery dependency.

The host and cluster control plane are IPv6-first. The approved [guest network proposal](VIRTUAL_NETWORK_PLAN.md) explicitly supports **both IPv4 and IPv6 inside guest segments**, even where older project descriptions imply IPv6-only guests. Ring 0 provides isolation, scheduling, physical memory, virtualization, and local IPC; network policy, coordination, storage services, and management remain Ring 3 responsibilities.

The initial quorum design assumes **crash faults and partitions, not Byzantine nodes**: admitted hosts and their enforcement services behave correctly until they crash or become unreachable. Guests, network traffic, and unauthenticated operators are untrusted. A compromised admitted host or administrator is outside the consensus/fencing guarantee; authenticated encryption alone cannot make such a host honest.

## Node enrollment and secure control — proposed

1. An authorized administrator initializes a cluster identity and trust root through a protected local bootstrap procedure. Every node generates a unique key pair locally using suitable entropy and protects its private key; enrollment verifies proof of possession and issues a certificate binding the cluster and stable node ID to that key. Discovery addresses and advertisements are only hints, never authorization. For the first cluster, provision the same administrator-signed genesis record naming the initial three nodes and their public keys on their independent local bootstrap media. Reject conflicting genesis records; the first election still requires two of those three nodes, not a unilateral bootstrap quorum.
2. Admit, remove, or replace a node through the quorum-backed membership record. A new node catches up as a non-voting learner before promotion. Membership changes use a safe joint transition requiring the appropriate old and new majorities; an enrolled certificate alone does not grant current membership. Reject duplicate identities and conflicting keys. An administrator can revoke, rotate, and recover keys and the trust root, with audited procedures and a plan for lost credentials; a removed or compromised key must not regain access on reconnect.
3. Use mutually authenticated, encrypted, integrity- and replay-protected standard transport for remote management, membership, and DIPC control traffic. Bind the authenticated node and operator authority to each operation; the existing shared HMAC tag is not a substitute. In secure cluster mode, reject privileged remote operations arriving only through the legacy shared-key path rather than leaving it as a parallel bypass. Guest Ethernet is a separate data plane, with its own authenticated overlay and port bindings in the [virtual network plan](VIRTUAL_NETWORK_PLAN.md).
4. **Host-node** UEFI Secure Boot, TPM-backed key protection and measured-boot attestation are optional **future** node-admission enhancements. If an operator selects an attestation requirement, validate a fresh challenge and an approved measurement chain and fail closed when unavailable; a self-reported manifest is not attestation. Do not claim that those enhancements are available today. This is separate from the [guest UEFI Secure Boot and vTPM](VIRTUALIZATION_PLAN.md#secure-boot-and-guest-variables) required by the proposed Windows 11 acceptance profile.

Each node must boot its local kernel, essential Ring-3 services, trust material, local membership/bootstrap metadata, and authorized rescue administration from local resources independent of a cluster volume or support VM. A node can be diagnosed and recovered offline; recovery cannot silently turn a partitioned cluster member into an independent writer.

## Quorum, durable storage, and fencing — proposed

- Initial distributed protection group: **three data nodes**, a durable **2-of-3 metadata quorum**, and **two full durable copies of every acknowledged write on different nodes**. These are separate requirements: quorum alone is not data durability. Write a new immutable or copy-on-write generation and checksum on two eligible independent nodes and persist both with real flush/FUA; preserve the prior committed generation until a metadata majority durably commits the new generation, checksum, placements, and fencing epoch. Only then acknowledge the write. A guest flush is an ordered durability barrier for earlier writes. The existing storage path does not satisfy this contract.
- A majority may continue only while it can meet both requirements. After one node fails, new writes require durable copies on both surviving nodes; earlier data may temporarily have only one verified surviving copy and must be repaired to a second node before being called protected again. If a majority, two durable destinations, valid ownership, or safe capacity is missing, reject writes or report unavailable/read-only rather than acknowledge unsafely. Replicas are not backups.
- Use a reviewed, published crash-fault majority-consensus protocol, independently implemented, for membership, desired state, policy revisions, and monotonically increasing ownership/fencing epochs. A minority may show explicitly stale local observations but cannot commit cluster mutations, grant new ownership, or authorize automatic restart.
- A timeout or heartbeat loss is only suspicion, not proof of death. Before starting a replacement instance or writer, obtain quorum authority **and** verify that the former owner cannot execute conflicting guest I/O or access its network and storage: for example, verified independent power fencing, or enforced fencing epochs at every storage and network access boundary. A guest must have no bypass around those boundaries. Fencing only remote storage or overlay access does not stop isolated local guest-to-guest traffic or local-volume I/O; those paths also need verified fencing or self-fencing. If fencing cannot be verified, leave the workload blocked; never automatically restart into a possible split brain.
- Time-based leases are safe only with documented bounds on clock drift/skew, lease duration, message delay, and suspend/reboot behavior, plus a trusted local self-fence that stops access before the lease can expire. Clock uncertainty, rollback, or loss of the enforcement service causes quarantine. Without those assumptions, do not treat lease expiry as proof of remote fencing; require independently verifiable fencing. Wall-clock certificate expiry likewise needs trustworthy time or a fail-closed alternative.

## Native management and operator workflow — proposed

One versioned Ring-3 management API is the authoritative interface for nodes, membership, VM lifecycle and consoles, networks and policy, volumes, health, and alarms. The native UI on **any healthy node** uses that same API, including when an operation targets another node. Existing `windowd`, `dashd`, `clusterd`, and `configd` are potential integration points, not proof that the API already exists. A browser interface is a later client of the same API, not a prerequisite or a separate source of truth.

- Authenticate operators and services for both local and remote sessions; authorize each action by scoped roles such as viewer, VM/network operator, and cluster administrator. Console access, enrollment, policy changes, fencing, and key management need explicit permissions. Reject unauthenticated or unauthorized requests at the API and at downstream capability boundaries.
- Version and negotiate API compatibility; reject unsupported or unsafe operations. Mutations carry an idempotency key scoped to the authenticated caller, operation, target, and request body. Persist the result with the quorum-committed operation so retries after a timeout cannot create duplicate VMs or replay an old change; conflicting reuse of a key is an error. A timeout is indeterminate until queried.
- Separate quorum-committed **desired** state from node-reported **observed** state, with revision, observation time/freshness, health, and explicit unreachable/stale markers. Report accepted, committed, reconciling, applied, blocked, or failed as distinct outcomes. In particular, committed policy is not necessarily globally enforced; see the [policy update protocol](VIRTUAL_NETWORK_PLAN.md#policy-updates-revocation-and-partitions--proposed).
- Record actor or unauthenticated attempt, action, target, revision, result, authorization denials, and relevant fencing evidence in a protected audit trail without recording credentials. Cluster mutations require durable audit recording; bounded local rescue audit records must be retained for later reconciliation. If required audit storage is unavailable, reject the mutation rather than silently omit it.
- In standalone/offline mode, authorized local recovery and explicitly local resources remain usable. Without quorum, cluster views are visibly stale/read-only and unsafe cluster mutations, remote ownership changes, and failover are refused; an unavailable console or operation reports its reason rather than implying success. Do not promote old observations to current state after reconnection without reconciliation.

## Acceptance tests — planned, not yet evidence of implementation

Run future integration tests against real Catenary nodes in QEMU and, for fencing and durability, suitable physical hardware; model tests alone do not prove these properties.

1. Bootstrap the same signed three-node genesis on all members; reject conflicting genesis and single-node quorum. Enroll using unique identities; reject an unknown, duplicated, expired, revoked, or wrong-cluster credential, forged admission, replayed control request, and an unavailable required attestation. Rotate a key and show that the old key cannot rejoin. Verify no plaintext or shared-key fallback, including privileged requests on the legacy path.
2. Partition the nodes 2+1 and then 1+1+1. Only a qualified majority can commit; minorities show stale/read-only state. Demonstrate two independently flushed data copies before each acknowledged write, and reject writes without two eligible copies. Crash at the data/metadata acknowledgement boundaries and verify recovery.
3. Lose a VM host, including an unreachable host that is still running. Prove a timeout alone never starts a duplicate; restart only after quorum and verifiable fencing. Exercise failed fencing, lease expiry, clock rollback, node reboot, and healing; stale writers and attachments remain blocked.
4. From each healthy node's native UI, authenticate as different roles, inspect nodes and VMs, create and retry a VM request, use an authorized console, configure a network/policy and inspect a volume. Verify authorization denials, one audit record per committed operation, idempotent retry, desired versus observed revisions, and explicit unreachable, stale, no-quorum, and read-only outcomes. Verify local rescue with cluster storage and any support VM unavailable.
5. Execute the local/remote switch, spoofing, fragment, revocation, overlay, and network-failure cases in the [network acceptance plan](VIRTUAL_NETWORK_PLAN.md#acceptance-tests--planned). Verify the UI never reports global policy enforcement while any affected attachment is neither updated nor verifiably fenced.
