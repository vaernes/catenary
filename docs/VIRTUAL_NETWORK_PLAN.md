# Virtual Guest Networking Plan

**Status: partial implementation; acceptance gates not passed.** The policy core and a fail-closed local guest-frame path exist, but this is not a complete virtual network. This is an independently authored Catenary design, not copied or adapted platform code. Published specifications and well-understood protocols may be used, with reviewed cryptography. The primary execution path is direct Type-1 virtualization; an optional support VM is not a network, bootstrap, or recovery dependency.

## Baseline and boundary

[virtio-net](../src/vmm/virtio_net.zig) contains guest queue handling and a DIPC handoff to `netd`; the [MicroVM bridge](../src/vmm/microvm_bridge.zig), [router](../src/ipc/router.zig), and [netd](../src/user/netd.zig) provide other existing transport pieces. They do **not** establish a secure guest vSwitch, microsegmentation policy, host-assigned guest identity, or encrypted multi-node overlay. [DIPC](../src/ipc/dipc.zig) currently uses a shared cluster HMAC, with the [known no-replay gap](PHASE_7_ROADMAP.md); neither that key nor guest-supplied MAC/IP addresses is identity.

The current partial path additionally uses [virtual_switch.zig](../src/user/protocols/virtual_switch.zig) for bounded IPv4/IPv6 TCP/UDP classification, host-provided MAC/IP bindings, per-port ingress/egress rules, attachment generations, and policy revisions. Guest TX is identified by its kernel-generated MicroVM endpoint, never parsed as a `netd` command, and cannot fall through to raw NIC transmit. Local `configd` may request attach/detach and revision-checked policy updates. Only `netd` may request the kernel to queue a policy-approved frame for a currently running VM. Since no guest ports are configured at startup, the implemented data path is default-deny. This path has unit/build coverage but no multi-guest integration evidence.

Not implemented in this partial path: an operator-facing configuration producer, address/bootstrap protocols (ARP, NDP, DHCP, DNS), flow state, remote overlays, authorized uplinks, comprehensive fragment/extension-header handling, counters, and complete detach/stop/restart cleanup. Do not treat the current TCP/UDP policy parser or the path wiring as satisfying the acceptance matrix below.

Keep device access and packet switching, policy, overlay, and address management in Ring 3, using capability-limited handoffs and the proposed [buffer ownership contract](DIPC_OWNERSHIP.md#guest-data-plane-buffers-and-grants--proposed-not-implemented). Ring 0 supplies physical isolation, local IPC, scheduling, and virtualization primitives. DIPC control messages and guest Ethernet frames are distinct planes and must not be interpreted interchangeably.

Host/cluster control and the overlay underlay are IPv6-first. Guest segments support **IPv4 and IPv6**, including dual-stack guests, even though older project descriptions prescribe IPv6-only guests. Guest IPv4 connectivity to an external network requires an explicitly configured gateway or translation path; it is not implied by an IPv6-only underlay.

## Local switches, ports, and identity — proposed

- A local Ring-3 virtual switch connects host-managed vNIC ports to logical layer-2 segments. Each segment has a stable, cluster-scoped ID and is isolated from other segments unless an explicitly authorized router or uplink connects them. A segment can exist on one node or extend to enrolled nodes; MAC learning is scoped to the segment.
- The host assigns stable VM and vNIC/port identities, independent of guest configuration, and binds each attachment to exactly one authorized segment, owning node, and monotonically changing attachment generation/ownership epoch. A VM can have multiple vNICs; a hot-unplug/re-attach or ownership move invalidates the old generation. MACs, IPv4/IPv6 addresses, and permitted prefixes are controlled attributes of that port, not its identity.
- Guest TX is **egress** from the guest port; delivery to a guest is **ingress** to the destination port. Authenticate the host-controlled source attachment, validate the Ethernet frame and allowed source MAC/IP, then enforce source egress policy. Learn only validated, authorized source bindings. The forwarding database is a bounded, aging hint, not an authority that lets a guest move or claim another port's MAC.
- Deliver known unicast only to an eligible port in the same segment. Broadcast, multicast, and unknown unicast may flood only to eligible ports within that segment, subject to quotas and **separate source egress and destination ingress decisions for every recipient**. Enforce both decisions for local and remote forwarding alike; no flooding, learned entry, promiscuous guest, or remote tunnel bypasses policy.
- A support L1 VM that multiplexes multiple nested L2 guests presents only its host-visible L1 port/principal. The host cannot claim per-L2 firewall isolation from L1-provided MACs, IPs, or tags. Such a claim requires a separately proven, host-controlled binding that L1 cannot forge and that identifies each L2 attachment; otherwise treat all multiplexed L2 traffic as the L1 principal.

## Stateful policy and bootstrap — proposed

Each port has ingress **and** egress rules, default-deny in both directions. An allowed new flow must satisfy the source egress and destination ingress rules; bounded state permits only corresponding return traffic and is tied to both attachment generations and the active policy revision. Unknown protocols, unclassifiable packets, missing policy, exhausted state, and unauthorized destinations fail closed. Policy revocation invalidates relevant state and queued packets rather than allowing established flows indefinitely.

Anti-spoof checks require the source MAC and IPv4/IPv6 addresses or prefixes to match host-authorized bindings. Address allocation, DHCP leases, static addresses, IPv6 link-local/SLAAC or privacy addresses must be registered or explicitly authorized before ordinary traffic; conflicts are rejected. Guest assertions and learned addresses cannot grant themselves authority.

The default-deny policy must include explicit, narrowly scoped bootstrap rules where configured:

- Permit necessary ARP requests/replies and IPv4 address-conflict probes, including a zero sender address only for valid bootstrap/probe traffic. Validate advertised bindings; do not allow arbitrary ARP claims.
- Permit required ICMPv6/NDP, including neighbor and router solicitation/advertisement, duplicate-address detection with the unspecified source, relevant multicast, and Packet Too Big/error messages needed for IPv6 operation. Validate message form and scope; router advertisements and other router-only messages are accepted only from authorized router ports.
- Permit DHCPv4 and DHCPv6 discovery, requests, and responses only along the configured client-to-trusted-server path. Only an authorized server may supply an address; apply the validated lease to the port binding before ordinary use. Drop rogue server responses.
- Permit DNS over UDP/TCP only to configured resolvers when that bootstrap service is enabled. These exceptions are scoped by segment, direction, port, and service; they are not blanket permission for other guest traffic or a substitute for application policy.

Parse IPv4 fragments and IPv6 extension-header chains under explicit length, depth, time, and memory bounds. For transport-aware decisions, hold fragments until a bounded, unambiguous reassembly permits classification; enforce the decision per destination before releasing the original fragments. Drop and count incomplete, malformed, overlapping, conflicting, unsupported, or over-limit packets rather than treating non-initial fragments or unknown extension headers as allowed. Handle IPv6 atomic fragments separately and honor the IPv6 overlapping-fragment rules. No fragment or cached decision may outlive its policy/attachment generation.

## Authenticated multi-node overlay — proposed

The initial overlay is a versioned Catenary framing protocol over IPv6/UDP, protected by mutually authenticated [DTLS 1.3](https://www.rfc-editor.org/rfc/rfc9147) associations. It uses unique enrolled node keys and the membership process in [cluster orchestration](CLUSTER_ORCHESTRATION.md#node-enrollment-and-secure-control--proposed), not the existing shared HMAC. The Catenary framing and transport integration are independently authored from published specifications; use reviewed existing Zig standard-library cryptographic primitives when suitable, and subject the resulting protocol implementation to independent review and interoperability tests. Any other third-party runtime crypto implementation needs explicit user approval under the [project rules](../.agents/workflows/project-rules.md). No invented cryptographic primitives or copied/adapted platform implementation.

- Negotiate the overlay version and required features within the authenticated association; reject unknown mandatory fields, unsupported versions, unauthorized peers, and downgrade/plaintext fallback. Disable replayable 0-RTT data. Require DTLS record anti-replay windows even though DTLS permits replay detection to be optional; reject duplicates/too-old records, use fresh association keys on reconnect or reboot, and rekey before protocol limits. DTLS datagrams can be lost or reordered; neither delivery nor ordering is promised.
- Each protected record carries a bounded header containing cluster and segment IDs, authenticated source node ID, source port ID and attachment generation, ownership/policy revision, payload length, and the Ethernet frame. Protect the header and frame together for confidentiality and integrity; underlay node addresses, packet sizes, and timing remain observable. The receiving node verifies the peer certificate and current membership, then verifies that its committed attachment grant binds that peer to the claimed source port, segment, and generation. Guest bytes never select or authorize the source identity.
- Only authenticated member nodes with authorized attachments for the segment receive encapsulated traffic. On reception, validate length, version, membership, binding, freshness, and segment; reject forged or stale metadata before forwarding. Apply the same source egress and per-destination ingress decisions as the local path, including anti-spoofing and stateful flow rules. Replication to a remote node must not turn segment membership into blanket ingress permission.
- Bound association, handshake, per-peer, per-segment, and per-port queues, packet rates, learning entries, and connection state; reserve resources for management. Count authentication failures, replay, stale policy, spoofing, malformed packets, congestion, and quota drops. Packet loss, link failure, or queue pressure drops or reports traffic; never fall back to an unprotected transport.

### MTU and underlay failure

Account for the underlay IPv6/UDP headers, DTLS expansion, overlay header, and the encapsulated Ethernet frame. The first version requires a verified path MTU large enough to carry the configured guest link MTU, including an IPv6 guest packet of at least 1280 bytes, plus all encapsulation overhead. Advertise a guest MTU no greater than the smallest admitted path can support. If an eligible path cannot meet that requirement, do not attach/extend the segment over it; on a later reduction, stop affected forwarding, count/report the failure, and use an authorized router to signal Packet Too Big where appropriate. Never truncate frames or silently advertise an IPv6 MTU below 1280. Bounded authenticated overlay fragmentation is a separate future design, not assumed here.

## Policy updates, revocation, and partitions — proposed

1. Commit a versioned policy and attachment binding through the cluster quorum. Authenticate distribution to each affected enforcement point; install atomically per port and acknowledge the applied revision only after old queued packets, conflicting grants, and disallowed stateful flows have been drained or invalidated. Hotplug starts quarantined until the current binding and policy are installed. A hot-unplug or move revokes the old generation before enabling a new owner.
2. **Committed is not globally enforced.** Report a revocation as globally enforced only when every affected attachment has applied it or is verifiably fenced/quarantined from all relevant local, overlay, uplink, and storage paths. Until then, report pending/blocked and identify unreachable or stale attachments. A disconnected node may continue using its previously valid lease briefly; a majority's commit does not retroactively stop it.
3. Missing, invalid, known-stale, or expired policy/binding/lease fails closed, including existing flows. A disconnected node must self-quarantine when its bounded authorization lease expires; if self-fencing cannot be trusted and independently verified under the stated assumptions, use external fencing and do not claim global enforcement. Fencing the overlay alone is insufficient if an affected local port can still reach local guests or an uplink. Reconnection requires fresh membership, policy, and attachment epochs before traffic resumes.
4. Leases require documented bounds on clock skew/drift, message delay, lease duration, and suspend/reboot behavior and a trusted monotonic enforcement timer. Those bounds must be established and validated for the deployment before leases are enabled; this plan assumes no numerical values. Uncertain time, rollback, or enforcement-service failure quarantines the port; without those assumptions, do not infer remote fencing from elapsed time. The management API distinguishes desired, committed, local applied, globally enforced, stale, and unreachable states.

An explicitly provisioned **standalone** node can operate local segments offline under its authorized local policy and local administration without a cluster or remote services. This is a separate mode, not a way for a partitioned cluster member to ignore cluster revocation or create a competing attachment. A cluster-managed port remains subject to its lease and fencing rules.

## Uplinks, lifecycle, and observability — proposed

Attach an uplink or gateway only through an explicitly authorized host-managed port and segment mapping. Routed, bridged/trunked, or translated paths must enforce the same source and destination policy and anti-spoof rules; prevent guest-controlled VLAN tags, direct NIC access, DMA, or passthrough from bypassing the switch. Untrusted or guest-assigned DMA devices require verified IOMMU isolation or equivalent hardware confinement; bounce buffers alone do not contain arbitrary DMA. A trusted host-owned device may use controlled bounce buffers for intended transfers. External IPv4 requires an approved IPv4-capable route or translation; local IPv4 communication does not require the host control plane to use IPv4.

Hotplug, detach, VM restart, node migration, and service restart update attachment generations and revoke old grants, learned entries, in-flight packets, and flow state. Fail closed during incomplete transitions. Expose bounded per-port/segment/peer packet and byte counters, policy allow/deny and bootstrap counters, spoof/replay/parse/MTU/queue drops, lease/revision status, and quota alarms through the versioned management API. Local traffic can continue during a remote link failure only while its own authorization remains valid.

## Acceptance tests — planned

These are future implementation requirements, not current passing tests. Use unit/model tests for parsers and state machines plus real multi-guest, multi-node QEMU integration; include suitable physical-host tests for DMA isolation and actual network/fencing failures.

1. **Local switching:** On one offline standalone node, attach dual-stack guests to two segments. Verify permitted IPv4 and IPv6 flows, denied ingress and egress, allowed stateful replies, known unicast learning, and unknown/broadcast/multicast flooding only within the segment and only to individually authorized recipients.
2. **Bootstrap and spoofing:** Exercise authorized ARP, NDP, DAD, DHCPv4/v6, DNS, and ICMPv6 Packet Too Big. Reject forged MAC, IPv4/IPv6 sources, ARP/NDP claims, rogue DHCP/RA, unapproved address changes, and cross-segment traffic; confirm counters. A multiplexed L1 cannot gain claimed per-L2 isolation by forging identifiers.
3. **Remote equivalence and authentication:** Repeat the same allow/deny matrix across two enrolled nodes. Capture traffic to verify guest frames and overlay segment/source-port metadata are not plaintext; reject altered records, replay, wrong cluster/node identity, forged segment/source port/generation, revoked keys, unsupported versions, and attempted plaintext/shared-key fallback.
4. **Fragments and bounds:** Test IPv4 and IPv6 valid, reordered, missing, overlapping, tiny, and malformed fragments; IPv6 atomic fragments and excessive/unknown extension chains; deny when transport classification is ambiguous. Verify no policy bypass, bounded memory/time, counters, and release on timeout.
5. **Revocation and lifecycle:** Revoke an established flow while packets are queued; verify flow state and old grants cannot deliver after local application. Partition an affected node and confirm the UI stays pending until it applies the revision or is verifiably fenced; test lease expiry, clock uncertainty, reconnect, hotplug, move, service restart, and stale generations.
6. **Network and resource failures:** Drop, duplicate, delay, reorder, and corrupt overlay packets; change PMTU below the supported threshold; disconnect an uplink; saturate queues, flow tables, and handshake limits. Verify fail-closed behavior, correct counters, bounded reclamation, no cross-segment leakage, and no downgrade.
7. **Operator flow:** From the native UI on each healthy node, authenticate, create a segment, attach vNICs, set and revoke rules, inspect desired/observed/revision and counters, and verify role denials and audit. Simulate an unreachable node and loss of quorum; show stale/read-only or blocked outcomes, never an unverified global-enforcement success.
